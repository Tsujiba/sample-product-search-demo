# 構成A/B 比較評価 & 検索精度チューニング

## 構成比較

| 項目 | S3 Vectors (構成A) | OpenSearch Serverless (構成B) |
|---|---|---|
| **検索方式** | ベクトル類似度のみ | ハイブリッド（ベクトル + BM25全文検索） |
| **日本語対応** | Embeddingモデル依存 | kuromoji による形態素解析 + Embedding |
| **部分一致** | 不可 | BM25で対応（「ボストン」→「ボストンバッグ」） |
| **コスト** | 従量課金のみ（$0〜） | 最低1 OCU（約$175/月） |
| **セットアップ** | シンプル | Collection + ポリシー + Pipeline + インデックス設計 |
| **レイテンシ** | 数百ms | 数百ms（同等） |
| **フィルタ** | メタデータフィルタ | keyword/range/bool フィルタ |
| **スケール** | 自動 | OCU自動スケール |
| **精度（意味検索）** | ○ Embeddingの品質次第 | ○ 同じEmbedding使用 |
| **精度（キーワード）** | △ 意味的に近くないとヒットしない | ◎ BM25で正確なキーワードマッチ |

### 精度差が出るケース

| クエリ例 | S3 Vectors | OpenSearch (Hybrid) |
|---|---|---|
| 「撥水 バッグ」 | Embeddingの意味理解に依存 | BM25で「撥水」テキスト一致 + ベクトル類似 |
| 「6950円のバッグ」 | 価格情報はEmbeddingに弱い | text_contentに価格記載あればBM25でヒット |
| 画像クエリ（類似商品） | ベクトル類似度で検索 | 同等（knnのみ使用） |
| 「旅行 整理整頓」 | 意味的に近い商品をヒット | 意味検索 + テキスト一致の両方で補完 |

## ドキュメント設計: 分離 vs 統合

### 現在の設計: Embedding種別ごとにドキュメント分離

1商品 = 最大2ドキュメント（`embedding_type: "image"` / `"text"`）

### 代替案: 1商品1ドキュメントに統合

```json
{
  "product_id": "uuid-xxx",
  "product_code": "A00001",
  "product_name": "やわらかボストンバッグ",
  "category": "バッグ",
  "text_content": "◆キャッチコピー...",
  "image_embedding": [0.012, ...],
  "text_embedding": [0.045, ...],
  "price": 6950,
  "image_s3_key": "products/images/A00001.jpeg"
}
```

### 比較分析

| 観点 | 分離（現在） | 統合（1商品1ドキュメント） |
|---|---|---|
| **ドキュメント数** | 商品数 × 2 | 商品数 × 1 |
| **ストレージ** | テキストフィールド（product_name, text_content）が重複格納される | 重複なし、効率的 |
| **knn検索** | 1つの `embedding` フィールドに対して検索、`embedding_type` でフィルタ | 2つのknn_vectorフィールドに対して別々にクエリが必要（OpenSearchは1クエリ1フィールド制約） |
| **ハイブリッド検索** | knn + BM25 を1クエリで実行可能 | image_embedding検索時とtext_embedding検索時で別クエリ → マージ処理が必要 |
| **検索ロジックの複雑さ** | シンプル（1クエリ、フィルタで切替） | 複雑（2クエリ実行 → アプリ側でスコアマージ） |
| **スコアリング** | search pipelineで正規化・合成が完結 | アプリ側で2クエリのスコアを正規化・合成する必要あり |
| **S3 Vectorsとの比較公平性** | ◎ 同じマージロジックで条件が揃う | △ 検索パスが異なり純粋な比較が困難 |
| **更新・削除** | 2ドキュメント操作が必要（IDなし自動生成のため全件検索で特定） | 1ドキュメント操作で完結（ただしAOSSはID指定不可） |
| **部分登録（画像のみ/テキストのみ）** | 該当ドキュメントだけ作成すればよい | null embeddingの扱いが必要（knn検索でエラーになる可能性） |
| **インデックスサイズ** | knn_vectorフィールド1つ → HNSWグラフ1つ | knn_vectorフィールド2つ → HNSWグラフ2つ（メモリ消費増） |
| **OCUコスト** | HNSWグラフ1つ分のメモリ | HNSWグラフ2つ分のメモリ（OCUスケールに影響する可能性） |
| **レイテンシ** | 1クエリで完結 | 2クエリ直列 or 並列実行が必要 |
| **将来の拡張（動画Embedding等）** | `embedding_type: "video"` ドキュメントを追加するだけ | フィールド追加 → インデックス再作成が必要 |
| **フィルタ精度** | `embedding_type` フィルタでpre-filter可能（knn対象を絞れる） | フィールド指定で検索対象を選択 |

### 結論

**現在の分離設計を採用した理由:**

1. **比較の公平性**: S3 Vectorsと同じ「画像/テキスト別インデックス → マージ」のパターンを踏襲し、バックエンド差異のみを純粋に比較できる
2. **検索のシンプルさ**: OpenSearchの1クエリで knn + BM25 ハイブリッド検索が完結する
3. **拡張性**: 新しいEmbedding種別（動画、音声等）の追加がドキュメント追加だけで済む
4. **部分登録対応**: 画像なし商品でもテキストドキュメントだけ登録すればよい

**統合設計が適するケース:**

- 商品数が非常に多く、ストレージ/OCUコストを最小化したい
- 検索対象が常に画像+テキスト両方で、片方だけの検索が不要
- 商品単位の更新・削除が頻繁に発生する（ただしAOSSのID制約で恩恵は限定的）

## 5万商品規模でのコスト・スケーラビリティ

### データ量の試算

| 項目 | 分離設計 | 統合設計 |
|---|---|---|
| ドキュメント数 | 10万件（5万 × 2） | 5万件 |
| ベクトルデータ量 | 1024次元 × float32 × 10万 = 約400MB | 1024次元 × float32 × 10万 = 約400MB（同じ） |
| テキストフィールド重複 | 平均2KB × 5万件 = 約100MB余分 | なし |
| 合計インデックスサイズ概算 | 約600MB | 約500MB |

### OpenSearch Serverless (AOSS) のコスト影響

AOSS は OCU 単位で課金（1 OCU = 6GB RAM, $0.24/時）。

| 項目 | 分離設計 | 統合設計 |
|---|---|---|
| HNSWグラフ数 | 1（embeddingフィールド1つ） | 2（image_embedding + text_embedding） |
| HNSWメモリ使用量 | ベクトル10万件 × ~6KB/件 ≈ 600MB | ベクトル5万件 × ~6KB/件 × 2フィールド ≈ 600MB |
| テキストインデックス | 10万ドキュメント分 | 5万ドキュメント分（約半分） |
| 推定必要OCU（検索） | 1〜2 OCU | 1〜2 OCU |
| 推定必要OCU（インデックス） | 1 OCU | 1 OCU |
| 月額コスト概算 | $175〜$350 | $175〜$350 |

**結論**: 5万商品規模ではどちらの設計でもOCU数に大きな差は出ない。AOSS の最小粒度が 0.5 OCU であり、600MB程度のインデックスは1 OCU内に収まる。

### S3 Vectors のコスト影響

| 項目 | 5万商品 |
|---|---|
| ベクトル数 | 10万件（画像5万 + テキスト5万） |
| ストレージ | 約400MB |
| クエリコスト | $0.01/1000クエリ程度 |
| 月額コスト概算（1万クエリ/月） | 数ドル |

**S3 Vectorsは5万商品でもコスト面で圧倒的に有利。** 固定費がなく、クエリ量に比例するのみ。

### スケーラビリティ比較（5万商品）

| 観点 | S3 Vectors | OpenSearch Serverless |
|---|---|---|
| **登録スループット** | API制限あり（バッチ対応で緩和可能） | バルクAPI対応、高スループット |
| **検索レイテンシ** | P99 数百ms（インデックスサイズに依存少） | P99 数百ms（OCU数でスケール） |
| **同時検索数** | S3基盤で自動スケール | OCU自動スケール（上限設定可能） |
| **初期データ投入** | 5万件 × Embedding生成 ≈ 数時間（Nova API制限） | 同上 + OpenSearchバルク投入は高速 |
| **インデックス更新** | 即時反映 | ニアリアルタイム（数秒のラグ） |
| **10万→50万商品への拡張** | 追加コスト微増のみ | OCU自動増加（コスト線形増） |

### 5万商品での推奨

| ユースケース | 推奨構成 |
|---|---|
| コスト最優先、ベクトル検索のみで十分 | **構成A（S3 Vectors）** — 月額数ドル |
| 全文検索・ハイブリッド検索が必要 | **構成B（OpenSearch）** — 月額$175〜 |
| 将来的に100万商品以上を想定 | **構成B** — OCU自動スケールで対応可能 |
| 検索精度を最大化したい | **構成B** — BM25 + ベクトルの補完効果 |
| PoC/検証フェーズ | **構成A** — コストゼロに近い状態で検証可能 |

## 検索精度チューニング

### 1. Embedding品質の改善

| チューニング項目 | 内容 | 影響範囲 |
|---|---|---|
| **テキスト前処理** | 商品説明から不要な記号・定型文を除去し、意味のある情報のみをEmbedding化 | 構成A/B共通 |
| **テキスト分割戦略** | 長文をチャンク分割してそれぞれEmbedding化 → 部分的な意味一致を拾える | 構成A/B共通 |
| **画像前処理** | 背景除去、商品部分のクロップ、複数アングル画像の個別登録 | 構成A/B共通 |
| **Embeddingモデル変更** | Cohere Embed、Titan Embeddings V2 等との比較検証 | 構成A/B共通 |
| **Embedding次元数** | 1024 → 512/256 に削減してノイズ低減（精度とのトレードオフ） | 構成A/B共通 |

### 2. 構成A（S3 Vectors）固有のチューニング

| チューニング項目 | 内容 |
|---|---|
| **距離メトリック変更** | cosine → dotProduct / euclidean の比較検証 |
| **検索対象の重み付け** | 画像インデックスとテキストインデックスの結果マージ時に重み付け（例: 画像0.7 + テキスト0.3） |
| **メタデータフィルタ** | カテゴリ等でpre-filterし、検索空間を絞ることで精度向上 |
| **top_K拡大 + リランキング** | 多めに取得してからアプリ側でリランキング（Cross-Encoder等） |

### 3. 構成B（OpenSearch）固有のチューニング

| チューニング項目 | 内容 |
|---|---|
| **ハイブリッド重み調整** | knn:BM25 の比率を 0.6:0.4 から調整（商品特性に応じて） |
| **正規化手法** | min_max → l2 / RRF (Reciprocal Rank Fusion) への変更 |
| **BM25 boost調整** | `product_name` と `text_content` のboost比率を調整 |
| **Analyzer変更** | kuromoji のフィルタ追加（kuromoji_stemmer等）、カスタムユーザー辞書追加 |
| **同義語辞書** | 「バッグ」=「鞄」=「カバン」等の同義語展開でBM25のリコール向上 |
| **ストップワード** | 「の」「で」「を」等を除外してBM25精度向上 |
| **フィールドブースト** | カテゴリ一致時にスコアを加算する function_score の導入 |
| **knn ef_search調整** | HNSW の探索パラメータ（ef_search）を増やして再現率向上（レイテンシとのトレードオフ） |
| **Multi-match戦略** | `best_fields` → `cross_fields` / `most_fields` の比較 |

### 4. アプリケーション層のチューニング

| チューニング項目 | 内容 | 構成 |
|---|---|---|
| **リランキング** | 初回検索結果をCross-Encoder（例: Cohere Rerank）で再スコアリング | A/B共通 |
| **クエリ拡張** | LLMでクエリを言い換え・補完してから検索（例:「赤い靴」→「赤 スニーカー レッド シューズ」） | A/B共通 |
| **フィードバックループ** | クリック/購買データを収集し、検索結果の重み付けに反映 | A/B共通 |
| **カテゴリ推定 + フィルタ** | クエリからカテゴリを推定し、pre-filterで検索空間を絞る | A/B共通 |
| **マルチステージ検索** | 粗い検索（top_100）→ 精密リランキング（top_10）の2段階 | A/B共通 |

### 5. 評価方法

| 手法 | 説明 |
|---|---|
| **nDCG@K** | 上位K件の順位付き適合度。検索結果の順序の質を評価 |
| **Recall@K** | 正解商品が上位K件に含まれる割合 |
| **MRR** | 最初の正解商品の順位の逆数の平均 |
| **A/Bテスト** | 同一クエリセットで構成A/Bの結果を比較（精度比較UIで実施可能） |
| **ユーザー評価** | 検索結果に対する主観的な適合度スコア（1-5段階） |

### 6. チューニング優先度（推奨順）

1. **テキスト前処理の改善** — 最もコストが低く効果が大きい
2. **ハイブリッド重み調整**（構成B）— search pipeline の weights 変更のみ
3. **同義語辞書の追加**（構成B）— 日本語ECでのリコール改善に直結
4. **リランキング導入** — 精度の上限を引き上げる（コスト増）
5. **Embeddingモデル比較** — モデル変更は全データ再投入が必要
